# 백오피스·플러터 통합 및 품질 개선 계획

## 1. 현황 요약

| 구분 | 백오피스 (Next.js) | 플러터 앱 |
|------|---------------------|-----------|
| **인증** | Cookie 세션 (POST /api/auth → account 쿠키) | Supabase Auth (signInWithPassword) + SharedPreferences 보조 |
| **데이터** | API 라우트(Admin) + 일부 컴포넌트에서 createClient() 직접 호출 | Repositories + **일부 화면에서 supabase 직접 호출** (schedule_tab, suggestions_tab, chat, bug_report) |
| **NEIS** | /api/neis-academic-sync → DB 동기화 | Edge Function `neis_academic_calendar` 직접 호출 |
| **결과 처리** | toast 성공/실패 | try/catch, 일부만 사용자 피드백 |

공통점: 동일 Supabase 프로젝트·동일 테이블(profiles, announcements, polls, suggestions, chat_rooms 등) 사용.

---

## 2. 목표 원칙

- **구동 원리 통일**: "한 번 정의한 규칙은 백오피스·앱에서 동일하게 동작" (같은 테이블·같은 의미·같은 보안 모델).
- **연동 보장**: 앱에서 작성한 데이터는 백오피스에서 그대로 관리 가능, 백오피스에서 만든 계정으로 앱 로그인 가능.
- **품질·확장성**: Result 패턴, 계층 분리, 공통 계약(이름·필드·에러 의미)으로 신규 기능을 같은 패턴으로 이어붙이기.

---

## 3. 아키텍처 정렬

```
[Backoffice]                    [Flutter App]
Components → API Routes         Screens → Repositories
     ↓        ↓                       ↓
Supabase Client  Supabase Admin    Supabase Client
     ↓                ↓                  ↓
     └────────────────┴──────────────────┘
                      │
              Supabase DB (공통)
                      │
              공통 계약 문서 (테이블·API·에러 코드)
```

- **백오피스**: 민감·권한 필요한 작업은 API → Admin만 사용.
- **플러터**: **모든 데이터 접근은 Repository만** 사용. 화면에서 supabase 직접 호출 제거.
- **공통**: 테이블·컬럼·에러 의미를 한 문서에 정리해 두 코드베이스가 따름.

---

## 4. 인증·구동 원리 통일

- **유지할 방향** (최소 변경으로 연동 유지):
  - 계정 생성: **백오피스에서만** (profiles + auth.users 생성). 앱은 로그인만.
  - 앱 로그인: **Supabase Auth** (이메일: `학번@school.local` 또는 `학번-profileId@laon.local`, 비밀번호: profiles와 동기).
  - 백오피스 로그인: **POST /api/auth** (학번+비밀번호) → 쿠키. 유지.
- **문서화**: "인증 모델" 문서에 (1) 계정 생성 경로 (2) 앱 vs 백오피스 로그인 (3) profiles ↔ auth.users 대응을 정리.

---

## 5. 데이터 계층 정리

### 5.1 백오피스

- 삭제·수정·중요 생성은 **API 라우트 경유**. RLS 의존 직접 delete는 제거(예: 사용자 삭제 API 적용 완료).
- announcements, polls, suggestions 등 **쓰기**가 컴포넌트에서 createClient()로만 이루어지면, 필요 시 API 추가 후 fetch로 전환(점진 적용).

### 5.2 플러터 (같은 방식으로 수정)

- **원칙**: 모든 Supabase 데이터 접근은 **Repository**만. 화면/ViewModel은 Repository 메서드만 호출.
- **제거할 직접 호출**:
  - `schedule_tab.dart`: `supabase.from('schedule_items').insert/delete`, `personal_events` → ScheduleRepository에 메서드 추가 후 사용.
  - `suggestions_tab.dart`: `supabase.from('suggestions').insert` → SuggestionsRepository만 사용.
  - `suggestions_chat_screen.dart`, `chat_screen.dart`: 채팅 관련 → ChatRepository/SuggestionsRepository로 이전.
  - `bug_report_screen.dart`: `supabase.from('bug_reports').insert` → BugReportRepository(신규) 추가.
- **Result 패턴 도입**: Repository는 `Future<AppResult<T>>` 반환 (success(data) | failure(message, code)). UI는 성공 시 스낵바, 실패 시 에러 메시지 표시(백오피스 toast와 동일 원리).

---

## 6. NEIS 연동 통일

- **현재**: 백오피스 = /api/neis-academic-sync → DB. 플러터 = Edge Function `neis_academic_calendar` 직접 호출.
- **권장**: **단일 소스 = DB**. 백오피스 sync만 NEIS 조회. 플러터는 **DB 테이블**(neis_academic_events 또는 sync 대상 테이블)만 조회. Edge Function 제거 또는 레거시 폴백만 유지.
- ScheduleRepository.`fetchAcademicCalendar`를 "DB에서 학사일정 읽기"로 변경.

---

## 7. 공통 계약 및 확장성

- **공통 계약 문서** (`docs/data-contract.md` 등):
  - 테이블: profiles, announcements, polls, suggestions, chat_rooms, chat_messages, schedule_items, personal_events, neis 관련 테이블.
  - 주요 컬럼, 의미, "앱 쓰기 가능 / 백오피스 전용".
  - 에러 코드: network_error, auth_error, not_found, validation_error 등.
- **확장 시**: 새 기능 = (1) 계약 문서 업데이트 (2) 백오피스 API/Admin (3) 플러터 Repository (4) 화면은 Repository + AppResult만 사용.

## 8. 구현 순서 제안

| 단계 | 내용 |
|------|------|
| 1 | **공통 계약 문서 초안**: 테이블·주요 API·에러 코드 정리. |
| 2 | **플러터 AppResult 도입**: `lib/core/result/app_result.dart` (success T \| failure message/code). Repository 반환 타입을 점진적으로 AppResult로. |
| 3 | **플러터 직접 호출 제거**: schedule_tab, suggestions_tab, suggestions_chat_screen, chat_screen, bug_report_screen → Repository만 사용. 필요 시 Repository 메서드 추가. |
| 4 | **플러터 UI 피드백 통일**: failure 시 스낵바/다이얼로그 (백오피스 toast와 동일 원리). |
| 5 | **NEIS 단일 소스**: 플러터 학사일정을 DB 조회로 변경. Edge Function 의존 제거. |
| 6 | **인증 문서화**: 계정 생성·앱 로그인·이메일 형식 문서에 명시. |
| 7 | **(선택) 백오피스 쓰기 API 정리**: announcements 등 쓰기를 API 경유로 점진 이전. |

---

## 9. 기대 효과

- **구동 원리 동일**: 데이터는 Repository/API만, 결과는 Result/toast로 명시적 처리.
- **연동**: 같은 DB·같은 계정·NEIS는 한 곳(sync)에서만 가져오고 앱은 DB만 읽음.
- **품질**: 실패 시 failure 반환 + 사용자 피드백; 새 기능은 계약 → API/Repo → UI 순으로 확장 가능.
